# Grafiko — Sistema de Gestión de Imprenta

## Identidad

- **Proyecto**: Grafiko (nombre visible en UI: "Grafiko" en todos lados — 2026-08-04 se eliminó el nombre "GestiPrint" que quedaba en index.html, manifest PWA, Layout, Login, Register, Products, App.tsx y seed.sql)
- **Para quién**: negocio propio del usuario (imprenta), no un cliente externo
- **Tipo**: comercio / pyme, single-tenant (un solo local/negocio, sin multi-sucursal)
- **Supabase project ref**: `eoznwxfflcmpivnwafwd` (región us-east-1, Postgres 17)
- **Estado**: en desarrollo/pruebas (deploy en Vercel existe, pero la base de Supabase todavía tiene datos de testing, no es producción real todavía — confirmado por el usuario el 2026-07-07)

## Stack técnico

- React 19.2 + TypeScript + Vite 8
- Supabase JS v2 (`@supabase/supabase-js` ^2.103.2)
- React Router v7, Zustand (auth store), React Hook Form, React Query, react-hot-toast
- Tailwind CSS v4, Recharts/Chart.js para gráficos
- jsPDF + jspdf-autotable para generación de PDFs (recibos, cuentas corrientes)
- Lucide React + Material Symbols para iconografía

## Estructura de carpetas

```
src/
  pages/          — una página por ruta (DashboardPage, KanbanPage, ClientsPage, BillingPage, ProductsPage, ConfigDropdownPage, CashRegisterPage)
  components/     — modales y piezas reutilizables (ClientModal, ClientLedgerModal, PaymentModal, AdjustmentModal, JobModal, BillingModal, Layout)
  store/          — Zustand (authStore.ts)
  lib/            — cliente Supabase (supabase.ts)
  utils/          — helpers (printJob.ts)
supabase/
  migrations/     — migraciones SQL versionadas (única fuente de verdad del schema)
```

**Desviación conocida respecto a buenas prácticas**: no existe carpeta `services/`. Los componentes llaman a `supabase` directamente (import de `lib/supabase.ts`). Si se refactoriza esto en el futuro, hacerlo de forma incremental, no como bloqueo de otras tareas.

## Base de datos (schema real, no genérico)

El modelo **no** usa nombres genéricos tipo `ventas`/`pagos`/`caja_sesiones`. Usa:

- `t_clientes` — clientes, con `situacion_iva`, `es_mayorista` (**columna deprecada desde 2026-08-25** — la distinción mayorista/minorista se sacó de toda la UI; la columna sigue en la base sin romper nada pero ya no se lee ni se escribe desde el frontend), `rubro_id` (**nuevo, 2026-08-26**, FK a `t_conf_rubros_cliente`, reemplaza al viejo campo de texto libre `rubro` que queda intacto pero sin uso desde `ClientModal.tsx` — ver Fase 8)
- `t_trabajos` — el equivalente a "venta"/orden de trabajo. Tiene `estado` (incluye `ANULADO` desde 2026-08-25, usado como borrado lógico — es `text` libre, sin `CHECK constraint`, así que agregar valores nuevos no requiere migración), `fecha_aprobacion`, muchos campos técnicos de imprenta (acabados, soportes, tamaños, película, etc.). **`total` ya NO se manda desde el frontend** (ver "Cálculos movidos a Supabase" más abajo) — lo mantiene un trigger sobre `t_trabajo_productos`.
- `t_trabajo_productos` — ítems de producto por trabajo. `producto_id` es nullable (ítems manuales sin catálogo). `nombre` (agregada 2026-08-25) guarda el nombre cuando es un ítem manual, o hace de override; `printJob.ts` resuelve el nombre real con `item.nombre || producto.nombre || 'Producto'`. `subtotal` es **columna generada** (`cantidad * precio_unitario`, calculada por Postgres) desde 2026-08-25 — un INSERT/UPDATE que intente escribirle un valor manual falla con error.
- `t_comprobantes` — facturación (tipo, número, `estado` enum `t_estado_comprobante`). `total` es **columna generada** (`subtotal + iva`) desde 2026-08-25 — `subtotal`/`iva` se siguen tipeando a mano en `BillingModal.tsx` (dependen de la situación fiscal, no se pueden derivar solos), pero `total` ya no se manda.
- `t_comprobante_items`, `t_comprobante_trabajos`, `t_comprobante_cobros`
- `t_recibos` — recibos de cobro a cuenta corriente (no ligados a un trabajo específico)
- `t_recibo_items`, `t_recibo_trabajos` (aplicación FIFO de recibos contra trabajos), `t_recibo_facturas`
- `t_pagos_trabajo` — pagos directos imputados a un trabajo puntual
- `t_ajustes_cc` — **(nuevo, 2026-07-06)** notas de crédito/débito manuales sobre cuenta corriente. Enum `t_tipo_ajuste_cc` (`credito`/`debito`), monto siempre positivo.
- `t_aperturas_caja` — apertura/cierre de caja (`fecha_apertura`, `fecha_cierre`, `saldo_inicio`, `saldo_cierre`). **Desde 2026-09-14 la caja nunca queda cerrada** (ver Fase 9): al "cerrar" un turno se abre otro inmediatamente. **Gap conocido**: no hay ninguna columna que guarde la diferencia del arqueo (sobrante/faltante) — se calcula en el frontend solo para mostrarla en el momento del cierre y no se persiste en ningún lado, ni siquiera en Supabase. Si en algún momento hace falta auditar histórico de arqueos, hay que agregar esa columna.
- `t_movimientos_caja` — **(nuevo, 2026-07-07)** ingresos/egresos de una caja abierta. Enum `t_tipo_movimiento_caja` (`ingreso`/`egreso`). FK a `t_aperturas_caja`, opcional a `t_recibos`/`t_pagos_trabajo`. Sin `cliente_id` directo (se obtiene vía `recibo_id`).
- `t_usuarios`, `t_roles` (roles existentes: **Administrador** = todos los permisos, **Operador** = gestión de trabajos y clientes)
- `t_proveedores`
- Tablas de configuración: `t_conf_acabados`, `t_conf_cant_copias`, `t_conf_peliculados`, `t_conf_sistemas_impresion`, `t_conf_soportes`, `t_conf_tamanios_papel`, `t_conf_terminaciones`, `t_conf_tipos_entrega`, `t_conf_tipos_gasto`

**Vista clave**: `v_saldo_clientes` — calcula `total_deuda`, `total_cobrado`, `total_ajustes_credito`, `total_ajustes_debito`, `saldo_pendiente` y `credito_disponible` por cliente, cruzando trabajos aprobados, comprobantes sueltos, pagos directos, recibos aplicados y ajustes manuales. Es la fuente de verdad del saldo — no recalcular esto a mano en el frontend.

**Vista**: `v_saldo_trabajos` — saldo pendiente por trabajo individual, usada para la imputación FIFO.

**Vistas de caja (nuevas, 2026-07-07)**: `v_caja_abierta` (la apertura de caja actual sin cerrar, o vacío) y `v_saldo_caja_actual` (saldo_inicio + ingresos - egresos de la caja abierta).

**RPC clave (nueva, 2026-07-07)**: `registrar_cobro_con_fifo(p_cliente_id, p_monto, p_metodo, p_fecha, p_observaciones, p_usuario_id)` — hace todo el flujo de cobro en una transacción atómica: crea el recibo (`t_recibos`+`t_recibo_items`), imputa FIFO contra trabajos pendientes del cliente (más antiguos primero, vía `v_saldo_trabajos`), y si hay una caja abierta registra el ingreso en `t_movimientos_caja`. Devuelve `recibo_id`, `monto_aplicado_fifo`, `monto_no_aplicado`, `movimiento_caja_id`. **El frontend debe llamar a este RPC en vez de replicar la lógica FIFO/caja en JS.** Es `SECURITY DEFINER` (detectado 2026-09-14 al auditar caja — ver nota abajo).

**RPCs y trigger nuevos (2026-08-25) — cálculos de plata movidos a Supabase**: ver sección "Cálculos movidos a Supabase (Fase 7)" más abajo para el detalle completo. En resumen: trigger `recalcular_total_trabajo` (mantiene `t_trabajos.total`), RPC `registrar_cobro_cierre_trabajo` (cobro atómico con descuento al cerrar un trabajo) y RPC `aplicar_credito_a_trabajos` (FIFO de crédito, unifica lo que antes estaba duplicado en `JobModal.tsx`/`ClientLedgerModal.tsx`). Estas 3 son `SECURITY INVOKER` (el default) — no usar `SECURITY DEFINER` salvo necesidad real, la RLS ya es permisiva para `authenticated`. **Corrección a esta regla (2026-09-14)**: no es cierto que "todas las funciones del proyecto son SECURITY INVOKER" — `registrar_cobro_con_fifo` (de la Fase 1, 2026-07-07) quedó como `SECURITY DEFINER`. Como la RLS ya es abierta para `authenticated`, no cambia el acceso real, pero si se audita esto de nuevo no asumir que está resuelto en todos lados.

**RPC de caja (nueva, 2026-09-14)**: `cerrar_y_reabrir_caja(p_apertura_id, p_saldo_contado, p_monto_retiro, p_metodo_retiro, p_motivo_retiro, p_usuario_id)` — cierra el turno de caja actual y abre uno nuevo en el mismo movimiento (ver Fase 9). `SECURITY INVOKER`.

RLS: todas las tablas `t_*` tienen policy `FOR ALL TO authenticated USING (true) WITH CHECK (true)` — control de acceso binario (autenticado sí/no), sin distinción real de roles todavía a nivel de RLS.

## Convenciones de código observadas

- Componentes funcionales con `React.FC`, hooks `useState`/`useEffect`/`useCallback`.
- Modales como componentes separados en `components/`, montados condicionalmente desde la página (`isXOpen && <XModal onClose={...} onSuccess={refetch} />`).
- Toasts con `react-hot-toast` para éxito/error en cada operación contra Supabase.
- Formularios con `react-hook-form` (`register`, `handleSubmit`, `formState.errors`).
- Estilo visual: Tailwind con clases largas, `rounded-[2rem]`/`rounded-[2.5rem]`, paleta `primary`/`error`/`emerald`/`indigo` con variantes `/10`, `/20` de opacidad, tipografía `font-headline font-extrabold`, labels en `text-[10px] font-black uppercase tracking-widest`.
- Íconos: `<span className="material-symbols-outlined">`.
- Montos: `Number(x).toLocaleString('es-AR', { minimumFractionDigits: 2 })`.
- Migraciones SQL versionadas en `supabase/migrations/` con timestamp `YYYYMMDDHHMMSS_descripcion.sql`; se aplican directo contra el proyecto remoto vía MCP de Supabase (no hay entorno local de Supabase corriendo en paralelo).

## Variables de entorno

No hay `.env.example` en el repo. Existe `.env` local con las variables esperadas según `lib/supabase.ts`:
- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`

Regla fija: nunca poner `service_role_key`, tokens de API ni certificados en variables `VITE_*` — esas van al bundle público del cliente.

**Incidente de seguridad y fix (2026-08-04)**: se detectó que `.env` estaba trackeado por git y público en GitHub (`daroylucas-byte/Imprenta_2026_grafiko`, repo público) desde el commit `8f5a27d` (2026-04-22) — causado por una línea corrupta en `.gitignore` (`. e n v` con bytes nulos intercalados) que nunca funcionó como patrón de ignore. Confirmado por el usuario que `.env` solo contenía `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` (públicas por diseño, visibles igual en el bundle del cliente), así que no se rotó ninguna key. Fix aplicado: `.gitignore` reescrito con las entradas mínimas recomendadas (`.env*`, certificados, `.claude/settings.local.json`, `CLAUDE.local.md`, temporales de Supabase) y `.env` sacado del tracking hacia adelante con `git rm --cached` (commits `036804b`/`a5195bd`). **El archivo sigue visible en commits históricos** — no se reescribió el historial (`git filter-repo` + force-push) porque el usuario decidió que el riesgo real era bajo; si en el futuro se agrega algo más sensible a `.env` (o se decide limpiar el historial), evaluarlo de nuevo.

- **Fase 8 — Rubros de cliente + fix de trabajos anulados en cuenta corriente** — ✅ completa 2026-08-26.
  - **Rubros de cliente configurables**: tabla nueva `t_conf_rubros_cliente` (mismo shape que las demás `t_conf_*`, RLS "Allow all" igual al resto), agregada a `ConfigDropdownPage.tsx` bajo una categoría nueva "Clientes" (el CRUD es genérico sobre un array de tablas, agregar una es literalmente una línea). `t_clientes.rubro_id` como FK real (ver arriba).   - **3 bugs encontrados y corregidos, todos con la misma causa raíz (trabajos `ANULADO`/`CANCELADO` que seguían "vivos" en algún lado)**:
    1. `v_saldo_clientes` comparaba `t_trabajos.estado` contra `'cancelado'`/`'anulado'` en **minúscula**, pero la app usa mayúscula — Postgres compara texto exacto, el filtro nunca excluía nada. Un cliente de prueba tenía `total_deuda` inflada en **$209.140** por 8 trabajos anulados; después del fix bajó al valor real. Fix: `CREATE OR REPLACE VIEW` con el `ARRAY` corregido a mayúscula (no hizo falta `DROP`, el shape de columnas no cambió).

- **Fase 9 — Caja: cierre reabre automáticamente** — ✅ completa 2026-09-14. Disparado por una auditoría del usuario sobre "dónde se calcula qué" en caja (ver tabla de la sección RPCs arriba) que reveló que un cobro vía `registrar_cobro_con_fifo` **no queda registrado en caja si no hay ninguna apertura sin cerrar** (el RPC simplemente no inserta el `t_movimientos_caja` en ese caso, sin avisar) — o sea que si el usuario se olvida de abrir la caja, esos ingresos desaparecen del control de caja silenciosamente.
  - **Solución**: la caja **nunca vuelve a quedar cerrada**. El botón "Arqueo & Cierre de Turno" (antes "Arqueo & Cerrar Caja") en `CashRegisterPage.tsx` → `CerrarCajaModal` pasa a ser un flujo de 2 pasos: (1) arqueo, igual que antes (saldo del sistema, monto contado, diferencia mostrada); (2) pregunta "¿Necesitás retirar dinero antes de reabrir la caja?" — si no, reabre directo con el monto contado; si sí, pide monto/medio/motivo (mismo formato que el modal ya existente "Registrar Egreso") y valida que no se retire más de lo contado.
  - Todo el cálculo lo hace la RPC nueva `cerrar_y_reabrir_caja` (ver arriba), atómica: registra el retiro como egreso del turno que se cierra (si hay), cierra ese turno (`saldo_cierre` = lo contado, **antes** del retiro — decisión explícita del usuario, para que ese campo documente el arqueo real), y abre el turno siguiente con `saldo_inicio = contado - retiro`. Mismo patrón que las RPCs de la Fase 7 — si algo falla, no queda a mitad de camino.
  - El botón "Abrir Turno de Caja" (vista de caja cerrada) queda como estaba, para el bootstrap inicial o como recuperación manual si alguna vez la caja termina cerrada por fuera de este flujo.
  - Verificado con `tsc --noEmit`, `npm run build`, y 8/8 tests con `BEGIN/ROLLBACK` contra la base real (incluye el caso de intentar retirar más de lo contado, que la RPC rechaza sin dejar cambios, y la verificación de que después de cualquier cierre sigue habiendo exactamente 1 apertura sin cerrar). Commiteado y pusheado a `origin/main` el 2026-09-14 (`b57e744`).

## Pendientes conocidos

- No hay carpeta `services/` — las llamadas a Supabase están directo en componentes/páginas.
- No hay tests automatizados en el repo.
- Roles (`Administrador`/`Operador`) existen en `t_roles` pero no hay evidencia de que se apliquen a nivel de RLS o de UI (falta confirmar).
- La diferencia del arqueo de caja (sobrante/faltante) no se persiste en ningún lado, solo se muestra en el momento del cierre (ver `t_aperturas_caja` arriba) — no hay forma de auditar históricamente si hubo faltantes.
- `registrar_cobro_con_fifo` (Fase 1) quedó como `SECURITY DEFINER` mientras el resto de las funciones del proyecto son `SECURITY INVOKER` — inconsistente, aunque sin impacto real hoy porque la RLS ya es abierta para `authenticated`.

## Lo que NO hacer

- No deshabilitar RLS en ninguna tabla.
- No usar `service_role` key en el cliente — solo en contextos server-side (Edge Functions, backend propio) si se llegan a implementar.
- No poner secrets en variables `VITE_*`.
- No modificar `v_saldo_clientes` u otras vistas financieras sin revisar antes qué depende de ellas (`pg_depend`), porque Postgres no permite `CREATE OR REPLACE VIEW` si cambia el orden/nombre de columnas — requiere `DROP VIEW` + `CREATE VIEW`.
- No aplicar migraciones a la base remota sin confirmación explícita del usuario antes de ejecutar.
- No asumir el schema genérico de prompts externos (`ventas`, `pagos`, `caja_sesiones`) — este proyecto tiene su propio modelo (`t_trabajos`, `t_comprobantes`, `t_recibos`, etc.), documentado arriba.
